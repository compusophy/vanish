# vanish — rust/wasm rebuild

## why this exists

the previous harness ran its agent loop inside a vercel serverless function.
three consequences followed, and together they made the tool unusable:

1. **a run was bounded by a request.** `lib/agent.js` hard-killed itself at
   52 s (`RUN_HARD_DEADLINE_MS`), then reported the death as "the hobby-tier
   60s function cap". `vercel.json` had declared `maxDuration: 300` the whole
   time. the wall was in the code, not the platform.
2. **the staging area was per-request memory.** `lib/tools.js` created
   `staged: new Map()` per request, so every edit existed only inside the
   request that made it. a run that ended before `git_commit` lost everything.
   the transcripts show the loop: stage → die → "re-staging it right now" →
   die.
3. **the fix that was written was never wired.** `lib/llm-step.js`,
   `/api/agent/step` and `/api/git/commit-files` implemented a browser-owned
   loop, but `public/app.js` still called the old `/api/agent/run`. the
   rescue was dead code.

none of the three is a bug you fix. they are consequences of running a
long-lived, stateful process inside a short-lived, stateless container.

## what replaced it

the whole harness is one rust crate compiled to wasm and loaded twice.

```
browser tab
├── main thread   — boot_ui()      src/ui/       dom only
│                                  never calls an api, never runs the loop,
│                                  so "stop" is always responsive
│        ▲ Event          │ Command
│        │  (postMessage, typed both ways by src/protocol.rs)
│        │                ▼
└── web worker    — boot_worker()  src/worker.rs
                   ├── src/agent/mod.rs      the loop. no deadline exists.
                   ├── src/agent/llm.rs      openrouter, streamed
                   ├── src/agent/github.rs   blobs → tree → commit → ref
                   ├── src/agent/tools.rs    tool surface
                   └── src/platform/opfs.rs  the working tree, on disk
```

there is no server. openrouter and the github api both send
`access-control-allow-origin: *` and accept an `authorization` header, so the
browser is the only client. verified, not assumed.

### how each original failure is now structurally impossible

| old failure | why it cannot recur |
| --- | --- |
| run killed at a deadline | a worker has no request bound to it; there is no deadline to hit, and no clock-watching code left |
| staged edits lost | writes land in opfs immediately; they survive the run, a reload, a crash, and a closed tab |
| ui bricked by a dom/logic mismatch | both halves compile against `src/protocol.rs`; drift is a build error, and a missing element id is reported loudly rather than skipped |
| stop button unresponsive | the loop is on another thread and cannot starve the ui |
| partial multi-file commits | commits go through the git data api as one atomic tree update |

## javascript inventory

hand-written javascript, in full:

- `web/index.html` — 3 lines: `init()`, `boot_ui(workerUrl)`
- `web/worker.js` — 3 lines: `init()`, `boot_worker()`

`web/pkg/vanish.js` is generated by wasm-bindgen and is not authored or
edited. no node, no python, no runtime dependencies.

## running it

```sh
wasm-pack build --target web --out-dir web/pkg --no-typescript
cargo run --features devserver --bin serve      # http://localhost:8787
```

the dev server (`src/bin/serve.rs`) is std-only rust and exists purely
because wasm modules and workers need correct mime types over http. it is
never deployed — `web/` is plain static files and can be hosted anywhere,
or nowhere.

## credentials

**github oauth is gone, and cannot come back without a server.** the
authorization-code flow exchanges the code for a token using the client
*secret*; a secret shipped to a browser is not a secret. github's device
flow needs no secret, but its endpoints send no cors headers, so a browser
cannot call them either. browser-only therefore means a **fine-grained
personal access token**, scoped to this repository, `contents: read+write`.

**`OPENROUTER_API_KEY` is still set on the vercel project and is still
unreachable.** environment variables are injected into functions and builds,
never into a static page at runtime. nothing was deleted; there is simply no
longer any server-side code to read it.

by explicit decision, both credentials are **entered once in the settings
panel and stored in this browser's `localStorage`**. they never appear in
the deployed bundle and never cross the network from this app. the cost is
entering them per browser or device, and re-entering if site data is
cleared.

they could instead be inlined at build time from the vercel env vars, which
would restore the old zero-setup behaviour — but the key would then sit
inside a file the browser downloads, protected only by vercel's deployment
protection. that was considered and rejected.

because there is no sign-in, an unconfigured harness has to say so: on first
load it renders setup instructions rather than sitting there looking ready.
saving settings verifies both credentials for real — the openrouter key
against `/api/v1/key` (which also catches an exhausted balance) and the
github token against the repository (which also catches a token that can
read but not push) — and reports which half failed.

## over-the-air updates

the binary is stamped at build time with its commit (`build.rs` →
`VANISH_BUILD`). the ui polls the github branch head every 45 s; when the
head differs from the running build it shows the changelog between the two
and reloads itself. a reload is deferred while a run is in flight, then
applied when the run ends — the tree is durable either way.
